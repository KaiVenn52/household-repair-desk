  - heading "Inspiration" [level=2]
  - paragraph: "A repair can fall apart after everyone agrees to it. One person has the quote, another has the calendar, and the cheapest number may leave out parts. We focused on the moment after a plan is made: if nobody can be home anymore, that plan should lose its approval immediately."
  - heading "What it does" [level=2]
  - paragraph: Household Repair Desk follows a fictional leaking kitchen sink from report to a recorded household decision. It compares a $130 subtotal with unknown parts against a $145 quote that includes the standard seal, keeps the budget explicit, and chooses the earliest future time that works for the provider and someone at home.
  - paragraph: After Sam approves Monday, changing his availability withdraws the old plan and its approval. The planner can propose Tuesday with Alex, but Alex must review and approve that new proposal. An expired review can be renewed without reviving old consent. If both hosts are away, the app explains the calendar blocker instead of asking for a larger budget.
  - paragraph: The public demo needs no login or installation. Each browser receives an isolated demo household stored on the server; sessions expire after 48 hours. All identities, quote documents, providers and calendars are fictional. No contractor is contacted, no appointment is booked, and no payment is made.
  - heading "How we built it" [level=2]
  - paragraph: The same RepairDesk domain rules power the local Express application and a hosted Web Standards Worker. The official MCP SDK exposes eight tools using MCP 2025-11-25 and Streamable HTTP. Browser planning and availability changes invoke the actual HTTP MCP endpoint, not a label-only mock. The hosted endpoint is /api/mcp because the hosting gateway reserves /mcp; the local endpoint remains /mcp.
  - paragraph: Approval is a separate browser review operation requiring the exact current proposal, its version, an expiring confirmation secret and explicit consent. Tools cannot approve a plan. Public task responses omit confirmation secrets. Hosted storage uses D1 and revision checks to reject conflicting writes. A random HttpOnly browser cookie isolates visitors; it is a demo session, not real household identity verification.
  - paragraph: The Alexa+ experience is a clearly labeled deterministic simulation. There is no live Alexa device, production Amazon API or runtime language model connection.
  - heading "Challenges" [level=2]
  - paragraph: We had to distinguish an unknown final price from a lower subtotal, and a calendar problem from an insufficient budget. We also had to invalidate both pending and completed approvals after schedule changes, without erasing the decision history. Fixed example dates would expire before judging, so new tasks generate future sample slots while old tasks keep their original calendar snapshot.
  - paragraph: Public deployment exposed a reserved MCP path and a CSP incompatibility with the hosting edge. We moved the standalone hosted endpoint to /api/mcp, added a per-response script nonce, and repeated the full anonymous browser workflow against the deployed site.
  - heading "Accomplishments" [level=2]
  - paragraph: A complete public, working demo with explicit household approval, recoverable failures and actual MCP transport calls. All 22 domain/MCP tests pass. Browser verification covers budgets, unavailable slots, approval, cancellation, changed availability, expired reviews, restored hosts, saved selection and stale dates. A separate anonymous public test verifies the deployed workflow, two-session isolation, persistence, accessibility and 375/768/1280 pixel layouts. Linux CI also passes.
  - heading "What we learned" [level=2]
  - paragraph: An assistant should not treat a plan as authority to act. The useful work is keeping the scope, schedule and approval tied to the same current proposal, and being precise about what changed when that proposal stops working.
  - heading "What is next" [level=2]
  - paragraph: Authenticated household roles, live quotes, real calendar integration and an assistant model client. Each would retain the same explicit approval boundary; real external bookings or payments would require an additional reviewed action. No user study or measured financial savings are claimed.
  - heading "Testing instructions" [level=2]
  - paragraph: "Open the public demo. Report: The kitchen sink is leaking under the cabinet. Set the budget to 140 and select Find a plan: the complete scope cannot fit. Explicitly change the cap to 150, find the plan, review and approve as Sam. Select Sam can't cover Monday, then Find another time. Review the new Tuesday plan as Alex and approve afresh. Reload and inspect Decision history. Use fictional details only."
